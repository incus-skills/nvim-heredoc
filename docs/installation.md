# Installation and replacement

The initial replacement uses the same provisioning pattern as the previous implementation: a shell script emits the three small, function-wrapped ftplugin entrypoints and installs the tested Lua modules into the Neovim configuration. It does not require a plugin manager, a plugin runtime entrypoint, or a user-authored LazyVim specification.

## 1. Obtain the repository

Clone the repository or update an existing checkout:

~~~sh
git clone https://github.com/incus-skills/nvim-heredoc.git
cd nvim-heredoc
~~~

For an existing checkout, pull the revision you intend to install before running the provisioner.

## 2. Run the provisioner

The provisioner targets ${XDG_CONFIG_HOME:-$HOME/.config}/nvim by default:

~~~sh
bash scripts/install.sh
~~~

It requires Bash, install, tee, and glow. To test or target another configuration tree, set NVIM_CONFIG_DIR:

~~~sh
NVIM_CONFIG_DIR="$(mktemp -d)/nvim" bash scripts/install.sh
~~~

The script installs the repository's canonical Lua modules to:

- lua/nvim-heredoc/init.lua
- lua/nvim-heredoc/scanner.lua
- lua/nvim-heredoc/editing.lua

It generates the three filetype entrypoints:

- after/ftplugin/bash.lua
- after/ftplugin/sh.lua
- after/ftplugin/zsh.lua

Each entrypoint calls require("nvim-heredoc").setup_buffer(). The module implementation is copied from the checked-out repository; it is not duplicated inside the provisioner.

## 3. Replacement semantics

The three after/ftplugin files are provisioner-owned outputs. Running the script replaces those three files and the three module files listed above. This is intentional: those ftplugins were previously generated by the same provisioning approach and are being replaced, not preserved as independent user configuration.

The provisioner does not remove unrelated files, alter LazyVim plugin specifications, change Conform settings, or install a Neovim plugin checkout. If you have independently added unrelated settings to one of those three owned ftplugin files, move those settings elsewhere before provisioning.

The operation is repeatable: rerunning it installs the current checkout's module files and regenerates the same three ftplugin shims.

## 4. Verify in Neovim

Restart Neovim, open one file for each supported filetype, and check the attachment marker:

~~~vim
:set filetype?
:lua print(vim.b.nvim_heredoc_attached)
~~~

Expected filetypes are bash, sh, and zsh; the marker should print true in each. The marker is set by the buffer integration when the corresponding provisioned ftplugin calls setup_buffer().

Then use a disposable Bash file to check closer insertion and changed-range handling:

~~~bash
if true; then
<TAB>cat <<-EOF
<TAB>  payload with two leading spaces
<TAB>EOF
fi
~~~

Use literal TAB characters for the structural prefix. For the paste check, insert several body lines before the closer, including an empty line and a line beginning with spaces. The plugin should add the structural TAB prefix where needed without removing or changing payload spaces. Repeated edits should not duplicate the prefix.

Also confirm that an ordinary << heredoc remains unchanged. Finally, execute the disposable script with Bash and inspect the delivered output:

~~~sh
bash /path/to/heredoc-live-test.bash
~~~

For <<-, the shell strips leading TAB bytes from body lines and the terminator; it preserves leading spaces. A visually indented buffer is not sufficient evidence that the shell receives the intended payload.

If anything is unexpected, capture the buffer with visible whitespace (for example :set list) and collect :messages before changing other configuration.

## 5. Remove or roll back the provisioned implementation

To disable the implementation, remove only the three generated ftplugin shims and the installed module directory:

~~~sh
config="${XDG_CONFIG_HOME:-$HOME/.config}/nvim"
rm -f -- "$config/after/ftplugin/bash.lua" \
  "$config/after/ftplugin/sh.lua" \
  "$config/after/ftplugin/zsh.lua"
rm -rf -- "$config/lua/nvim-heredoc"
~~~

This removes the new implementation; it does not restore the previous implementation. To return to the previous behaviour, rerun the previous provisioning script after removing the new files.

## Current verification boundary

CI exercises the shared scanner, Neovim buffer integration, shell payload delivery, formatter behaviour, and a pinned LazyVim/plugin coexistence fixture. The fixture now loads the same per-filetype entrypoint shape produced by this provisioner. It is not the user's full configuration and is not a substitute for live verification in the target Neovim 0.12.4/LazyVim environment.

The Lua scanner remains deliberately conservative. Backtick substitutions, heredoc redirections inside command substitutions, multiline quoted commands, and other uncertain constructs are not safe editing targets. See the scanner limits in scanner.md.
